description: ユーザーが指定した固定点（コミット、ブランチ、タグ、merge-base）以降の変更を、2つの軸でレビューする：Standards（このリポジトリの文書化された規約に従っているか）と Spec（元の課題／仕様が求めたものと一致しているか）。両軸を並行したサブエージェントで実行し、並べて報告する。ブランチ、PR、作業中の変更のレビューを求められたとき、「X 以降をレビューして」と言われたときに使う。
---

ユーザーが与えた固定点と `HEAD` の間の diff を2軸でレビューする：

- **Standards**：コードがこのリポジトリの文書化された規約に従っているか
- **Spec**：コードが元の課題／仕様を忠実に実装しているか

両軸は**並行したサブエージェント**として実行し、互いのコンテキストを汚染しない。結果をこのスキルが集約する。各サブエージェントは新しいコンテキストウィンドウで始める。

仕様の出所（指示、仕様ファイル、タスクの記録）がこの会話で与えられていない場合は、ユーザーに確認する。

## 手順

### 1. 固定点を確定する

手順1の最初の操作の前に `date +%s` を取り、total の起点とする。

固定点は次のどれかで決まる。ユーザーが指定した場合はそれが常に優先する（この場合のモードは user-specified）。指定が無い場合、現在のブランチの前回レビュー（特定方法は手順6）があれば差し戻しモード：前回のヘッダに記録されたレビュー時点の HEAD を固定点にする。どちらでもなければ初回モード：固定点はリモートのデフォルトブランチで、`git symbolic-ref refs/remotes/origin/HEAD` で発見した `origin/<デフォルトブランチ>` を使う。発見できなければ聞く。

先へ進む前に、選んだモード・固定点・理由を1行で宣言する。差し戻しモードでは次を確認する：前回の HEAD が現在の `HEAD` の祖先であること（`git merge-base --is-ancestor <前回のHEAD> HEAD`）。前回の HEAD がデフォルトブランチの祖先でもある場合は、前回レビューはマージ済みの古いものとして初回モードに落とす。前回のモードが user-specified の場合と、前回の報告で Spec がスキップされている場合は連鎖させず、固定点を聞く。前回のヘッダにレビュー時点の HEAD の SHA が無い場合も連鎖させない。作業中のブランチにデフォルトブランチをマージした場合は、その変更が差分に入ることを宣言に含める。

diff コマンドを1回だけ確定する：`git diff <固定点>...HEAD`（3ドット。merge-base との比較になる）。コミット一覧も控える：`git log <固定点>..HEAD --oneline`。固定点が解決できること（`git rev-parse <固定点>`）と diff が空でないことを確認する。空かどうかは手順4の除外をする前の diff で判定する：差し戻しモードで空なら「前回レビュー以降に変更なし」と報告して終える。それ以外の空の diff と悪い参照は、2つのサブエージェントの中でなく、ここで失敗させる。サブエージェントを起動せずに終えるときも、手順5の Timing 行を出してから終える。wait は `0s`、起動しなかった軸は `not-run` とする。

### 2. 仕様の出所を特定する

元の仕様をこの順で探す：

1. コミットメッセージ内の参照（`#123`、`Closes #45`、タスク ID 等）から辿れる仕様・タスク記録
2. ユーザーが引数で渡したパス
3. ブランチ名や機能名に一致する、`docs/`、`specs/`、`.scratch/` 配下の仕様ファイル
4. 何も見つからなければ、仕様がどこにあるかユーザーに聞く。無いと言われたら、**Spec** サブエージェントはスキップし、「仕様が利用できない」と報告する

### 3. 規約の出所を特定する

コードの書き方を文書化したファイルを、リポジトリ内からすべて探す。ルールファイル（`.cursor/rules/`、`rules.ja/` 等）、`CODING_STANDARDS.md`、`CONTRIBUTING.md` が存在すれば、必ず一覧に入れる。あわせて、リポジトリの文書や `.gitattributes`（`linguist-generated`、`-diff` 等）が生成物やフィクスチャの期待出力として示すパスがあれば控える。手順4で diff から除外するために使う。手掛かりが無ければ除外はしない（推測で除外しない）。

リポジトリの文書に加えて、Standards 軸は常に下記の**スメルの基準線**を持つ：リポジトリが何も文書化していない場合にも適用される、Fowler のコードスメル（『Refactoring』第3章）の固定セットである。拘束する規則は2つ：

- **リポジトリが優先。** 文書化されたリポジトリの規約が常に勝つ。基準線が問題にしても、規約側がそれを是認している場合はスメルを抑止する
- **常に判断事項。** 各スメルはラベル付きのヒューリスティクス（「Feature Envy の可能性」）であり、硬い違反ではない。ここでの他の規約と同様、ツールが既に強制しているものは飛ばす

各スメルは「何であるか → 直し方」の形で書かれている。diff と照合すること：

- **Mysterious Name**（謎の名前）：何をするか／何を持つかが名前から分からない関数、変数、型。→ 改名する。正直な名前が思いつかなければ、設計が濁っている
- **Duplicated Code**（重複コード）：同じ形のロジックが変更内の複数の塊やファイルに現れる。→ 共通の形を抽出し、両方から呼ぶ
- **Feature Envy**（羨望）：自分のデータより他のオブジェクトのデータに手を伸ばすメソッド。→ そのメソッドを、羨望しているデータ側へ移す
- **Data Clumps**（データの塊）：同じ数個のフィールドや引数がいつも一緒に移動する（型になりたがっている）。→ 1つの型にまとめ、それを渡す
- **Primitive Obsession**（プリミティブへの執着）：独自の型を持つべきドメイン概念を、プリミティブや文字列で代用している。→ 概念に小さな独自の型を与える
- **Repeated Switches**（繰り返される分岐）：同じ型に対する同じ `switch`／`if` の連なりが変更内のあちこちに再現する。→ ポリモーフィズム、または両所で共有する1つのマップに置き換える
- **Shotgun Surgery**（散弾銃手術）：1つの論理的変更が、diff 内の多数のファイルへの散らかった編集を強いる。→ 一緒に変わるものを1つのモジュールに集める
- **Divergent Change**（変更の発散）：1つのファイルやモジュールが、無関係な複数の理由で編集される。→ 各モジュールが1つの理由で変わるよう分割する
- **Speculative Generality**（投機的な汎用性）：仕様に無い需要のために足された抽象、引数、フック。→ 削除する。本当の需要が来るまでインラインに戻す
- **Message Chains**（メッセージの連鎖）：呼び出し側が依存すべきでない長い `a.b().c().d()` のナビゲーション。→ 最初のオブジェクトの1メソッドの後ろに歩行を隠す
- **Middle Man**（仲介者）：ほとんど委譲するだけのクラスや関数。→ 取り除き、本当の対象を直接呼ぶ
- **Refused Bequest**（相続の拒否）：継承したものの大半を無視・上書きするサブクラスや実装者。→ 継承をやめ、合成を使う

### 4. 両サブエージェントを並行して起動する

両方のサブエージェント呼び出しを同時に出し、前景で実行して、返ってきた報告を集約する。

起動する直前に、オペレータへ1行出す。走らせる軸の名前と、起動した軸が全部返るまで待つこと。親は、起動直前と、起動したサブエージェントの結果が揃った直後の `date +%s` の差を wait とする。

手順3で控えた生成物・期待出力のパスがある場合、両サブエージェントに渡す diff コマンドにはそのパスを `':(exclude)…'` の pathspec で含め、除外分の `git diff <固定点>...HEAD --stat -- <除外パス>` の結果も渡す。

**両方の依頼に含めるもの**：

- 作業の最初と最終報告の直前に `date +%s` を取り、その差の整数秒を報告本文の最後の行へ `Elapsed: <秒>s` と書くこと
- 除外パスがあるときは、中身が要る指摘に限って `git diff <固定点>...HEAD -- <パス>` でその変更を見ること

**Standards サブエージェントへの指示**に含めるもの：

- diff コマンド全文とコミット一覧
- 手順3で見つけた規約の出所ファイルの一覧に、**手順3のスメル基準線を全文貼ったもの**（サブエージェントは他にそれへアクセスする手段を持たない）
- 依頼文：「ファイル／塊ごとに報告する：(a) diff が文書化された規約に違反する箇所すべて（規約を引用する：ファイル＋規則）、(b) 見つけた基準線のスメル（名前を挙げ、塊を引用する）。硬い違反と判断事項を区別する：文書化された規約の違反は硬くなり得るが、基準線のスメルは常に判断事項であり、文書化されたリポジトリの規約は基準線に勝つ。ツールが強制済みのものは飛ばす。400語以内」

**Spec サブエージェントへの指示**に含めるもの：

- diff コマンドとコミット一覧
- 仕様のパス、または取得した内容。仕様ファイルが 10KB を超え、見出しで節に分かれている場合は、パスに加えて、diff が触れた対象に対応する節の見出し文字列を渡す（対応する節が複数あれば全部）。節の範囲は、その見出しから次の同レベル以上の見出しの直前までとし、冒頭の共通部（最初の節見出しより前の部分）と、指名された節の終わりまでを読むよう指示する。見出しは `#` で始まる行として完全一致で探し、0件または複数件なら全文を読ませる。渡した節が他の節を参照している場合と、diff が渡した節に出てこない対象を触っている場合は全文を読ませる。10KB 以下の仕様は全文を渡す
- 差し戻しモードでは前回の review.md のパスも渡し、依頼文の (a) を「前回指摘した欠落が埋まったかを確認する」に読み替えさせる。(b)(c) は今回の差分を対象にする
- 除外した期待出力がある場合は、その stat も渡し、期待出力の変更は振る舞いの変更の証拠として扱うよう伝える
- 依頼文：「報告する：(a) 仕様が求めたのに欠けている・部分的な要件、(b) 求められていないのに diff にある振る舞い（スコープクリープ）、(c) 実装されているように見えるが実装が間違っていそうな要件。指摘ごとに仕様の行を引用する。400語以内」

仕様が無い場合は Spec サブエージェントを飛ばし、最終報告にその旨を書く。

### 5. 集約する

2つの報告を `## Standards` と `## Spec` の見出しの下に、そのまま、または軽く整えて提示する。所見を**混ぜたり、順位を付け直したりしない**。2軸を分けているのは意図的である（「なぜ2軸か」参照）。

最後に1行の要約を付ける：軸ごとの所見総数と、各軸内での最悪の指摘（あれば）。軸をまたいだ単一の勝者は選ばない：それは分離が防ごうとしている順位付けそのものである。

手順4で除外したパスがあれば、その一覧を報告に含める。

所見の要約のあと、チャットの末尾に次の1行を出す。`Timing: total <秒>s (<表示>); wait <秒>s (<表示>); standards <値>; spec <値>`。`<表示>` は分と2桁の秒（`6m03s`）である。3600秒以上は時間も付ける（`1h05m09s`）。1分未満の分は `0m` とする。`total` は手順1の最初に取った `date +%s` からこの行を書くまでの差である。サブエージェント報告の最後の `Elapsed:` 行は `## Standards` と `## Spec` へ入れる前に外し、`standards` と `spec` の秒にだけ使う。その行が無い軸は `unmeasured` とし、秒を作らない。Spec を起動しなかったときは `spec skipped` とする。

### 6. ファイルに書き出す

集約した報告を、対象リポジトリのルートの `var/reviews/` にも書き出す。チャットへの提示は従来どおり行い、ファイルは引き継ぎ用の写しである。

- 置き場所：`var/reviews/<日付>-<時刻>-<対象>/review.md`。日付と時刻は実行したマシンのローカル時刻（`YYYY-MM-DD` と `HHMMSS`）で、名前の辞書順が実行順になる。対象は現在のブランチ名（`/` は `-` に置き換える）で、人が見るための目印である。ブランチ名が取れない場合は固定点の短縮 SHA を使い、そのレビューは差し戻しの連鎖に使わない
- 中身：手順5の報告そのもの。先頭にヘッダを書く：実際に使った diff コマンド（除外の pathspec と stat 用コマンドを含む）、コミット範囲、モード（`Mode: initial | re-review | user-specified`）、固定点（`Fixed point: <解決済みの40桁 SHA>`）、レビュー時点の HEAD（`git rev-parse HEAD` の40桁 SHA。どちらの欄にも `HEAD` とは書かない）、ブランチ名（`Branch: <置き換え前の名前>`）、日時（タイムゾーンのオフセット付き）、チャット末尾と同じ Timing 行、レビュアー（実行したエージェントとモデル）。Timing 行は本文に繰り返さない
- 実行ごとに新しいディレクトリを作る。同じディレクトリが既にある場合は失敗させる（上書きしない）。前のレビューは残し、掃除はしない
- 前回レビューの特定（手順1で使う）：`var/reviews/` から `<日付>-<時刻>-` で始まるディレクトリだけを対象にし、ヘッダの `Branch:` が現在のブランチ名と一致するもののうち、名前の辞書順で最後のものを前回レビューとする。旧形式のディレクトリは対象にしない
- 対象リポジトリの `.gitignore` で `var/reviews/` が無視されているかを `git check-ignore -q var/reviews/` で判定し、無視されていなければ1行追加する
- 最後に、書き出したファイルのパスをユーザーに伝える

## なぜ2軸か

変更は一方の軸を通り、他方で落ちることがある：

- すべての規約に従うが、間違ったものを実装した → **Standards 合格、Spec 不合格**
- 課題が求めたとおりのことをするが、プロジェクトの慣習を壊した → **Spec 合格、Standards 不合格**

別々に報告することで、一方の軸が他方を覆い隠すのを防ぐ。
