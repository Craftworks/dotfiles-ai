# Git

履歴は、承認者が後から読んで判断するための記録である。因果が追えることを優先する。

## Branch（trunk-based）

- `main` が唯一の常駐ブランチ（trunk）。常に動く状態に保つ。`develop` 等の常駐ブランチは作らない
- 作業ブランチは `main` から切り、短命（目安1〜2日）にする
- ブランチ名は英語 kebab-case で、種類を接頭辞にする: `feat/` `fix/` `refactor/` `chore/`（例: `fix/daemon-heartbeat`）
- 小さく完結する変更は `main` へ直接コミットしてよい。リスクのある変更・複数ステップの変更はブランチを切る
- マージ前に履歴を整える（WIP コミットの squash、rebase）。`main` への force push と、共有済み履歴の書き換えは禁止

## Commit の原則

- 1コミット = 1意図（change-discipline と同じ）。無関係な変更を混ぜない。コミット前に staged diff を自分で確認する
- コミット／プッシュはユーザーの指示があるときだけ行う。指示なく履歴を進めない
- 秘密情報・生成物・一時ファイルをコミットしない（`.gitignore` を先に整える）

## Commit message

言語は **英語が既定**。プロジェクト側で変える場合は、同名のスキルを置かず、言語だけを指定する常駐ルール（Cursor では `.cursor/rules/commit-message-language.mdc`、Claude Code ではプロジェクトの `CLAUDE.md`）で上書きする（その場合も type / scope は英語のまま）。

形式（Conventional Commits）:

```
<type>(<scope>): <subject>

<body>

<footer>
```

- type は固定: `feat` `fix` `refactor` `test` `docs` `perf` `build` `ci` `style` `chore` `revert`
- scope は任意。影響範囲を短い英語名詞で（`daemon`、`billing` 等）。付けるなら一貫させる
- subject は命令形にする（add / fix / remove。過去形・進行形にしない）。先頭は小文字、末尾にピリオドなし、72文字以内（目安50）
- body は「何を」ではなく「なぜ」を書く（what は diff が語る）。1行72文字で折り返し、subject との間に空行を置く
- body は、subject だけで意図と理由が自明な小さい変更でのみ省略できる。設計判断、ファイルの追加・分離・廃止、複数ファイルに跨る変更では body を必須とし、なぜその構成にしたかと、何を残し何を捨てたかを書く
- 破壊的変更は footer に `BREAKING CHANGE: <内容>`、課題参照は `Refs: #123` の形で書く

### type の選び方

- `feat`: 利用者から見える新しい振る舞い・機能の追加（新しいコマンド、画面、API、設定項目、新しい仕組みや層の導入、新しいルール／スキルの追加）
- `fix`: 壊れていた振る舞いを仕様どおりに戻す（バグ修正）
- `refactor`: 外から見える振る舞いを変えずに内部構造だけを変える（分割、改名、移動、重複の除去）
- `perf`: 振る舞いを変えずに、計測に基づいて速度・メモリなどの性能を改善する
- `test`: テストだけの追加・修正（本体の振る舞いを変えない）
- `docs`: 人間が読むドキュメントだけの変更（README、仕様書、コメント）。エージェントの振る舞いを決めるテキスト（ルール、スキル、プロンプト）は、ファイル形式が文書でも docs ではない
- `build`: 成果物の作り方の変更（ビルド手順、依存関係、生成スクリプト）
- `ci`: CI の設定・ワークフローだけの変更
- `style`: 意味も構造も変えない見た目の変更（整形、空白）。構造を変えたら `refactor`
- `chore`: 上のどれにも当てはまらない保守（`.gitignore`、既存設定の維持、生成物の再生成、既存ルール／スキルの文面の強化・修正）。新しい仕組みの導入は `chore` ではなく `feat`
- `revert`: 以前のコミットの取り消し

迷ったらこの順で判定する: 新しい振る舞いがあるか（`feat`）→ 壊れたものを直したか（`fix`）→ 振る舞い不変で何を変えたか（構造は `refactor`、整形は `style`、性能は `perf`）→ 対象がテスト・人間向け文書・CI だけか（`test` / `docs` / `ci`）→ 作り方の変更か（`build`）→ 残りは `chore`。ファイルの追加そのものは `feat` の根拠にならない（テストファイルの追加は `test`、文書の追加は `docs`）

良い例:

```
fix(daemon): stop silent spin when frame counter stalls

The watcher kept looping on a stale frame number after the
daemon died. Add a heartbeat check so it exits with a reason.
```

悪い例（subject）: `fix bug` / `updated files` / `WIP` / `misc changes`

悪い例（body = 何の列挙。diff の繰り返しなので書かない）:

```
chore: import beta baseline

Add detect daemon, watcher scripts, action helpers, docs, and samples.
```

## Hooks

- フックは早期フィードバックであり、ゲートの正本は CI に置く。ローカル完結のプロジェクトでは、フック＋タグ前のフルチェックをゲート扱いにする
- フック定義はリポ内で管理し、ツールとバージョンを固定する。マシンローカルの `.git/hooks` だけにあるものを正としない。導入は1コマンドで再現できるようにする
- pre-commit は10秒以内を目安に、整形・lint・秘密情報スキャン・巨大ファイル混入チェックまで。コミットメッセージの形式検証は commit-msg で行う
- 型チェックとテストの速い範囲は pre-push へ。重いテストは pre-commit / pre-push に入れず、CI へ
- `--no-verify` はユーザーの指示があるときだけ使う。フックが落ちたら回避せず原因を直す。フック未導入の環境では、その旨を伝えてから進める
- フックが自動修正した差分は、再確認するまでコミットしない

## Tags

- リリースは `main` にセマンティックバージョンのタグを打つ（`v1.2.3`）。打ったタグは動かさない

## コミットの実行手順

ユーザーがコミットを求めたときは、ステージ済みの変更に対する `git commit` を1つ作る。いきなり実行はしない。プッシュはしない（承認後も含む）。

### 見る範囲

次を並行して実行する。

- `git status --short`
- `git diff --cached`
- `git log -8 --oneline`（scope と文体を既存の履歴に揃えるため）

メッセージに入れるのはステージ済みの変更だけ。ステージが空なら、その旨を書いてコマンドは作らない。関連する未ステージや未追跡のファイルがあれば、返信で名前を挙げ、メッセージには入れない。

ステージ内容が複数の意図に分かれる場合は、1つのメッセージにまとめず、分割を提案する。

秘密情報が含まれていたら、コマンドを作らず、そのファイルを示す。

### 作るもの

上の Commit message の規約に従い、この形のコマンドを1つ。

```bash
git commit -m "$(cat <<'EOF'
type: subject

body (why)

EOF
)"
```

### 実行の承認

- コマンドを作ったら、提示して **実行してよいかユーザーに確認する**（ターミナルに手で貼らせる前提にしない）
- 提示する文面が英語のときは、同じ返信でコマンドの前に、subject・body・footer の日本語訳をコードブロックで置く。承認者が英語の文面を読まずに判断できる長さにする。heredoc にはコミットに残る文面だけを置き、日本語訳はチャット側に置く
- 承認された場合のみ、そのコマンドをターミナルで実行する。実行したら、コミットハッシュと `git log -1 --oneline` の結果を報告する
- 承認されなかったら、コマンドをテキストとして残して終わる（後から手動で実行できるように）
- 実行が失敗したら、エラー内容をそのまま報告する。再試行やメッセージの書き換えは、ユーザーの指示を待つ
