# 仕様の細部を消す前の確認

仕様文書に書かれた振る舞いの細部を、文書から消してよいか確認する手順。
細部の記述はコードが持ち、テストはそれを公開面で独立に照合する。文書の散文は3番目の写しになるため、条件を満たせば消す。
発火の条件は、change-discipline の Done means（仕様の圧縮）に従う。
このファイルは手順だけを持ち、判定基準は change-discipline にある。

## 消せるもの

次の2点をどちらも満たす細部。

- コードがその細部を表している（検証の分岐、出力の形式、エラーの文面として実装にある）
- テストがその細部を公開面で固定している

対象の例：入出力のケースの列挙、正確なエラー文面、報告・出力の形式、境界値とその期待結果。

## 消せないもの

次はコードもテストも表せない。文書に残す。

- なぜと契約、非目標
- 完了条件（受け入れ水準そのもの）
- 意図的にテストしない範囲
- オラクルの独立性の条件（何を正解とするか。例：凍結したサンプルが正解であり、実装の出力から期待値を作らない）

コードもテストも、「書かれていないこと」と「期待値が実装から独立していること」を表せない。

## 手順

1. 項目ごとに、コードがその細部を表しているかを見る。表していなければ消す対象ではない（未実装の仕様か、実装の不足として扱う）
2. テストが固定しているかを見る。固定していなければ、文書の記述をオラクルにしてテストを書く／強くする。期待値は文書から取り、実装の現在の出力からは作らない
3. change-discipline の削除判定を適用する。判定を通らない項目は消さない。文書に残す
4. 節をまたいで繰り返されている文は、共通部に寄せて1回にする
5. 条件を満たした項目だけを、文書から消す。文面をテストやコードへ写すことはしない
6. スイート全体を回す
7. 完了報告に、消した項目と、文書に残した項目を添える

## 失敗モード

- 実装の現在の出力を期待値としてテストを書く。テストが実装に従属し、仕様としての独立性を失う
- 項目ごとに照合せず、まとめて消す。コードが表していない、またはテストが固定していない細部が、文書からも消える
- 細部の文面をテストやコードのコメントに写す。写しが増え、将来ずれる場所が増える
