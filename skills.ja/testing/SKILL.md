# Testing

テストは実装の正しさではなく、公開面の振る舞いが変更後も保たれることを保証する。テスト結果は、承認者が判断するための証拠である。

## 方針

- テストは公開面の振る舞い（入力 → 観測可能な結果）を検証する
- 配分はプロダクトの大きさではなく、複雑さと障害リスクの所在で決める。ロジックが複雑な所は単体テスト厚め、結線（API・DB・ファイル・プロセス間）が複雑な所は統合テスト厚め、E2E は重要フローだけ少数
- 純粋なロジック・述語・計算は高速な単体テストで、境界（正常・異常・空・上限）まで固定する
- 境界の統合テストは実物に近くする（実 DB・実ファイル・実サンプル）。モック／スタブは外部サービスとネットワーク境界に限る（詳細は [mocking.md](mocking.md)）
- 実サンプル・実データ・実障害由来の回帰ケースを資産として保持する。実障害は、直す前にケース化する
- バグ修正は、先に再現するテストを書く。公開契約や振る舞いの要になる部分もテスト先行にする
- テストを通すためにテストを弱めない（期待値の書き換え、アサーションの削除、skip や無効化）。テストの期待値は振る舞いの細部の正本であり、変えれば仕様の変更になる
- 期待値のほうが誤っていると判断したら、実装を止める。どのテストのどの期待値を、なぜ変えるかを承認者に示し、合意を得てから変える
- 仕様文書に書かれたテスト仕様をテストコードへ移植する手順は [spec-migration.md](spec-migration.md) を参照
- テストは決定的に保つ（実行順序・時刻・ネットワーク・環境に依存しない。状態はテストごとに初期化する）
- 一コマンドで実行でき、変更のたびに回せる速さを保つ。失敗したら原因が追える出力を残す
- 完了を報告する前に、スイート全体を回す。触ったテストだけを回して完了としない
- 報告には、実行したコマンドと結果を添える
- 失敗は件数でなく、テストの名前で挙げる。変更と無関係に見える失敗も省かない
- 仕様がエラーの形式（名前・原因・次のアクション）を定めている場合、テストはその文面まで固定する。名前や終了コードの確認だけで済ませない
- 「全件そろってから処理する」性質は、正常と異常が混在するケースで検証する。単独のケースでは、その性質に違反する実装が通ってしまう

## Seam：テストを置く場所

seam（継ぎ目）とは、テストを当てる公開境界のこと：内部に手を入れずに振る舞いを観測できるインターフェース。テストは seam に置き、内部に対しては置かない。

テストは、事前に合意した seam にだけ書く。テストを書く前に、対象の seam を書き出してユーザーと確認する。未確認の seam にはテストを書かない。すべてはテストできない。だから seam を事前に合意することが、テストの労力を「あらゆる端ケース」ではなく重要な経路と複雑なロジックに落とす方法である。

問う：「公開インターフェースは何か、どの seam をテストすべきか」。提案する seam ごとに、それが何を捕まえ何を取りこぼすかを1行で添える。

コードベースを探索するときは、用語集（`GLOSSARY.md` 等）があれば読み、テスト名とインターフェースの語彙をプロジェクトのドメイン言語に合わせる。触る領域の設計判断の記録（ADR 等）も尊重する。

インターフェースの形そのものが問題になっている場合（モジュールをどれだけ深くするか、seam をどこに置くか、インターフェースに何を公開するか）は、`architecture` ルールの語彙（Deep Modules、削除テスト等）を使う。あれは参照する語彙であり、実行するセッションではない。

良いテストと悪いテストの例は [tests.md](tests.md) を参照。

## ループの作法（テスト先行で進めるとき）

- green の前に red。失敗するテストを先に書き、それを通すのに必要なだけのコードを書く。将来のテストを先取りしたり、投機的な機能を足したりしない
- 一度に1スライス。1サイクルにつき seam 1つ、テスト1つ、最小の実装1つ
- 水平スライス（先にテストを全部書き、次に実装を全部書く）にしない。一括したテストは想像した振る舞いを検証する：物事の形をテストし、ユーザーに見える振る舞いをテストしないため、実際の変更に鈍感になり、実装の理解が進む前にテスト構造に固着する。垂直スライスで進める：テスト1つ → 実装1つ → 繰り返し。各テストは、前のサイクルで学んだことに応答する tracer bullet（曳光弾）である
- リファクタはループの一部ではない。リファクタはレビュー段階（`code-review` スキル参照）に属し、red → green の実装サイクルには属さない

## 反パターン

- カバレッジ％を目標にしない（未検証箇所を見つけるためには使う）
- 内部のメソッド呼び出し・呼び出し順・回数を検証しない（テストを実装に密結合させる）。内部の協力者をモックする、私有メソッドをテストする、副経路で検証する（インターフェースでなく DB を直接引く）も同種である。見分け方：振る舞いが変わっていないのにリファクタでテストが壊れる
- 同語反復（tautological）：期待値をコードと同じ方法で再計算する（`expect(add(a, b)).toBe(a + b)`、手で同じように導いたスナップショット、定数とそれ自身の比較）。構成上必ず通り、コードと決して食い違わない。期待値は独立した真実の源から取る：既知のリテラル、実例、仕様
- 時々落ちる（フレーキーな）テストを放置したり、無効化で済ませたりしない
- 全層モックで、実際には何も検証していない統合テストを作らない
- プロダクトの大きさでテスト戦略を切り替えない（育ったときに断絶する）

## Decision test

迷ったら: **実装をリファクタしても、振る舞いが同じなら通り続け、振る舞いが壊れたら落ちるテストか**

Decision test の使い方：仕様に違反する実装を1つ具体的に書き出し、その実装がこのテストを通るなら、テストを強くする
