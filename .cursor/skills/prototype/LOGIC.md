# Logic Prototype

ボタンをクリックして状態モデルを駆動できる、単一の自己完結した HTML ファイル（**共有可能なデモ**）。疑問が**ビジネスロジック、状態遷移、データの形**についてである場合に使う：紙の上では筋が通って見えるが、実ケースに通して初めて違和感が出る類のもの。

インストール不要の1ファイルなので、非開発者（デザイナー、PM、ドメインの専門家）に渡して、モデルを自分の手で触ってもらえる。だからコードの言葉ではなく、彼らの言葉で語る。

## この形が合う場合

- 「この状態マシンが、X の次に Y が来る端ケースを処理できるか分からない」
- 「このデータモデルで、あのケースを本当に表現できるのか」
- 「API を書く前に、その形の感触を掴みたい」
- **ボタンを押して状態の変化を見たい**、という類のもの全般

疑問が「これはどう見えるべきか」なら、この分岐は間違いである。[UI.md](UI.md) を使う。

## 手順

### 1. 疑問を明記する

コードを書く前に、どの状態モデルについて、どの疑問のプロトタイプなのかを書き出す。1段落で、デモの先頭に（コメントではなく、見える導入として）置く。間違った疑問に答えるロジックプロトタイプは純粋な無駄なので、後から（ユーザーが今見ていなくても、AFK で戻ってきても）確認できるよう、疑問を明示する。

### 2. ロジックを移植可能なモジュールに隔離する

実際のロジック（疑問に答えている部分）は、後で本物のコードベースへそのまま移せる小さな純粋モジュールとして、単一の `<script>` ブロックに置く。周囲のページは捨てだが、このモジュールは捨てではない。

適切な形は疑問によって変わる：

- **純粋な reducer**：`(state, action) => state`。アクションが離散的なイベントで、状態が単一の値である場合に良い
- **状態マシン**：明示的な状態と遷移。「今この瞬間、どのアクションがそもそも合法か」が疑問の一部である場合に良い
- **プレーンなデータ型に対する小さな純粋関数の集合**。暗黙の現在状態がなく、変換だけがある場合に良い
- **明確なメソッド面を持つクラスやモジュール**：ロジックが継続する内部状態を本当に所有している場合

ページへの配線のしやすさではなく、問われている疑問に最も合う形を選ぶ。純粋に保つ：DOM なし、`document` なし、ボタンハンドラが内部へ手を伸ばすこともなし。ページがモジュールを呼ぶのであって、その逆方向には何も流れない。これがプロトタイプをその寿命の先でも有用にする：疑問に答えが出たら、検証済みの reducer／マシン／関数集合がそのまま本物のモジュールへ移る。

### 3. 共有可能な HTML ファイルを作る

1ファイル、プレーンな HTML/CSS/JS：フレームワークなし、バンドラなし、サーバーなし、すべてインラインで、ダブルクリックで開き、メールで回しても生き残る。誰でも開くだけで実行できること。

非開発者向けに書く。すべてのラベルはコードではなく**ドメインの言葉**で：ボタンと状態は reducer ではなく業務の言葉で読めること。何が起きているかを平易な言葉で説明する。

上から下へ、明快な階層でレイアウトする：

1. **タイトルと1行の説明**：このデモで何を探索できるか（手順1の疑問）
2. **現在の状態**：関連する状態の全体を、読みやすいパネルとして描画する（生の JSON ダンプではなく、ラベル付きのフィールド）。クリックのたびに再描画して変化を見せる。非開発者が追いやすくなるなら、何が変わったかを明示する
3. **自由操作ボタン**：アクションごとに1ボタン、常時利用可能。誰でも任意の順序でモデルを突ける。各クリックでアクションを dispatch し、状態を再描画する
4. **ガイド付きウォークスルー**：**シナリオ**の集合、タブごとに1つ。各タブには、そのシナリオの平易な説明（どういう状況を用意し、何に注目すべきか）と、その下にそのシナリオで**押すボタンの列**を置く。各ステップは本物のボタンで、クリックするとそのアクションを実行して次のステップへ進む。ウォークスルーの開始時は既知の初期状態へリセットし、シナリオが毎回同じように走るようにする

紙の上では推論しにくい厄介なケースを示すシナリオを選ぶ：ハッピーパス、扱いにくい端ケース、不法であるべきことの試行。

美しく、しかし抑制的に保つ：明快なタイポグラフィ、広い余白、アクセントカラーは1色。アニメーションやギミックはなし：状態とボタンと競合するものは置かない。

### 4. 渡す

ファイルを送るか、開いて見せる。相手は好きなときにウォークスルーと自由操作をクリックして回る。面白い瞬間は「待って、それは可能であってはいけないはず」や「え、X は違うと思っていた」と言うときで、それこそが**アイデア側の**バグであり、この分岐の存在理由である。新しいアクションやシナリオが欲しいと言われたら追加する。プロトタイプは進化する。

### 5. 答えとプロトタイプを保存する

プロトタイプが疑問に答えたら、答えを保存し、次に [SKILL](SKILL.md) の記述どおりにプロトタイプを保存する。ロジック固有の対応：検証済みの reducer／マシン／関数集合は本物のモジュールへ移り（決定の取り込み）、HTML の殻はプロトタイプを一次資料として保持する捨てブランチに同行する。自己完結した1ファイルなので、そこでも自明に再実行できる。

## 反パターン

- **テストを足さない。** テストが要るプロトタイプは、もうプロトタイプではない
- **本物のデータベースに配線しない。** 疑問が永続化そのものについてでない限り、メモリ内の状態を使う
- **一般化しない。** 「将来 X に対応したくなったら」はなし。プロトタイプは1つの疑問に答える
- **ロジックとページを混ぜない。** 純粋モジュールが DOM、`document`、ボタンハンドラを参照したら、もう移せない。ページは純粋モジュールの上の薄い殻に保つ
- **フレームワーク、バンドラ、サーバーに手を伸ばさない。** 受け手がダブルクリックする1ファイル。React アプリや開発サーバーは「共有可能」を損なう
- **HTML の殻を本番へ出荷しない。** ページは手でクリックして回すために最適化されている。保持する価値があるのは背後のロジックモジュールである
