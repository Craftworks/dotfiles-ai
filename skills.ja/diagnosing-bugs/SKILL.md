# バグの診断

難しいバグのための規律。フェーズを飛ばすのは、明示的に正当化できるときだけ。

コードベースを探索するときは、用語集（`GLOSSARY.md` 等）があれば読んで関係モジュールのメンタルモデルを明確にし、触る領域の設計判断の記録（ADR 等）を確認する。

## 秘密情報を伏せる

このスキルではコマンド、出力、取得した成果物を見せる場面がある。**秘密情報は先に伏せる**：該当箇所を `<REDACTED>` に置き換える。ループは環境変数に対して組み、認証情報そのものではなく環境変数側が表示に残るようにする。取得した成果物には認証ヘッダーが含まれ得る：信号を持つ行だけを引用する。

伏せた出力では診断に足りない場合は、その旨を言ってユーザーに求める。

## フェーズ1：フィードバックループを作る

**このスキルはここにある。** 残りは機械的作業である。そのバグで赤くなる**タイトな**合否信号（フィードバックループ）があれば、原因は見つかる。二分探索も仮説検証も計装も、それを消費するだけだ。無ければ、コードをどれだけ睨んでも救われない。

ここに不釣り合いなほど労力をかける。**攻撃的に。創造的に。諦めない。**

### 作り方（だいたいこの順）

1. **失敗するテスト**：バグに届く seam（単体、統合、E2E）でのテスト
2. **curl／HTTP スクリプト**：動いている開発サーバーに対して
3. **CLI 実行**：フィクスチャ入力を与え、stdout を既知の良好なスナップショットと diff する
4. **ヘッドレスブラウザのスクリプト**（Playwright／Puppeteer）：UI を駆動し、DOM／コンソール／ネットワークを表明する
5. **取得したトレースのリプレイ**：実際のネットワークリクエスト／ペイロード／イベントログをディスクに保存し、そのコード経路だけに通して再現する
6. **使い捨てハーネス**：システムの最小部分（1サービス、依存はモック）だけを立ち上げ、バグの経路を1回の関数呼び出しで踏む
7. **プロパティ／ファズのループ**：「ときどき出力が間違う」型なら、ランダム入力を1000回流して失敗モードを探す
8. **二分探索ハーネス**：2つの既知の状態（コミット、データセット、バージョン）の間に出現したなら、「状態 X で起動、確認、繰り返し」を自動化し、`git bisect run` できるようにする
9. **差分ループ**：同じ入力を旧バージョンと新バージョン（または2つの設定）に通し、出力を diff する
10. **HITL bash スクリプト**：最後の手段。人間がクリックしなければならないなら、`scripts/hitl-loop.template.sh` で人間側を駆動し、ループの構造は保つ。取得した出力が自分に返ってくるようにする

正しいフィードバックループが作れれば、バグは90%直ったも同然である。

### ループをタイトにする

ループをプロダクトとして扱う。ループが**できたら**、次に**タイトにする**：

- 速くできるか（セットアップのキャッシュ、無関係な初期化の省略、テスト範囲の絞り込み）
- 信号を鋭くできるか（「クラッシュしなかった」ではなく、具体的な症状を表明する）
- 決定的にできるか（時刻の固定、乱数シードの固定、ファイルシステムの分離、ネットワークの凍結）

30秒かかるフレーキーなループは「無いのとほぼ同じ」だが、2秒で決定的なループはタイトであり、デバッグの超能力である。

### 非決定的なバグ

目標はクリーンな再現ではなく、**再現率を上げること**。トリガーを100回ループし、並列化し、負荷をかけ、タイミングの窓を狭め、スリープを注入する。再現率50%のバグはデバッグ可能で、1%は不可能。だからデバッグ可能になるまで率を上げ続ける。

### 本当にループが作れないとき

止まって、明示的にそう言う。試したことを列挙する。ユーザーに求めるのは：(a) 再現する環境へのアクセス、(b) 伏せ済みの取得物（HAR ファイル、ログダンプ、コアダンプ、タイムスタンプ付き画面録画）、(c) 本番への一時的な計装の許可。ループ無しに仮説へ進まない。

### 完了条件：赤くなり得るタイトなループ

フェーズ1は、ループが**タイト**で**赤くなり得る（red-capable）**ときに完了する。次を満たす**1つのコマンド**（スクリプトのパス、テストの実行、curl）を名指しでき、**既に少なくとも1回実行済み**であること（実行と出力を、伏せた上で見せる）：

- [ ] **赤くなり得る**：実際のバグのコード経路を駆動し、**ユーザーの症状そのもの**を表明するので、このバグで赤くなり、直れば緑になる。「エラーなく走る」では駄目で、この特定のバグを捕まえられなければならない
- [ ] **決定的**：毎回同じ判定（フレーキーなバグは前述のとおり再現率を高く固定する）
- [ ] **速い**：分ではなく秒
- [ ] **エージェントが実行できる**：無人で回せる。人間が介在するのは `scripts/hitl-loop.template.sh` 経由だけ

このコマンドが存在する前に、コードを読んで理論を作り始めている自分に気づいたら、**止まる：仮説へ直行することこそ、このスキルが防ぐ失敗そのもの**である。赤くなり得るコマンド無しに、フェーズ2は無い。

## フェーズ2：再現＋最小化

ループを回す。バグの出現で赤くなるのを見る。

確認事項：

- [ ] ループが出す失敗モードは、近くにある別の失敗ではなく、**ユーザー**が述べたもの
- [ ] 複数回の実行で再現する（非決定的なバグは、デバッグに足る再現率で）
- [ ] 症状そのもの（エラーメッセージ、間違った出力、遅いタイミング）を取得済みで、後のフェーズが「直ったこと」をそれと照合できる

### 最小化

赤くなったら、再現を**まだ赤くなる最小のシナリオ**まで削る。入力、呼び出し元、設定、データ、手順を**1つずつ**切り、そのたびにループを再実行し、失敗に荷重を持つものだけを残す。

なぜやるか：最小の再現はフェーズ3の仮説空間を狭め（疑うべき可動部が減る）、フェーズ5できれいな回帰テストになる。

完了は、**残った要素がすべて荷重を持つ**とき：どれか1つを外すとループが緑になる状態。

再現と最小化が済むまで進まない。

## フェーズ3：仮説

どれかを検証する前に、**ランク付けした仮説を3〜5個**生成する。仮説が1つだけだと、最初のもっともらしい考えに固着する。

各仮説は**反証可能**でなければならない：その仮説が立てる予測を述べる。

> 形式：「<X> が原因なら、<Y> を変えるとバグは消える／<Z> を変えると悪化する」

予測を述べられない仮説は雰囲気である：捨てるか、鋭くする。

**検証の前に、ランク付けした一覧をユーザーに見せる。** ユーザーはドメイン知識で即座に並べ替えることがよくある（「#3 はちょうどデプロイしたばかり」）、あるいは既に除外済みの仮説を知っている。安いチェックポイントで、大きな時間節約になる。ユーザーが不在なら止まらず、自分の順位で進める。

## フェーズ4：計装

各プローブはフェーズ3の具体的な予測に対応しなければならない。**一度に変える変数は1つ。**

道具の優先順位：

1. **デバッガ／REPL での検査**（環境が対応していれば）。ブレークポイント1つはログ10行に勝る
2. **対象を絞ったログ**：仮説同士を区別する境界に置く
3. 「全部ログして grep」は決してやらない

**すべてのデバッグログに一意な接頭辞を付ける**（例：`[DEBUG-a4f2]`）。後片付けが grep 1回になる。タグの無いログは生き残り、タグ付きのログは死ぬ。

**性能の分岐。** 性能リグレッションでは、ログは大抵間違った道具である。代わりに：基準の計測を確立し（タイミングハーネス、`performance.now()`、プロファイラ、クエリプラン）、それから二分探索する。計測が先、修正は後。

## フェーズ5：修正＋回帰テスト

回帰テストは**修正の前に**書く。ただし**正しい seam** がある場合だけ。

正しい seam とは、テストが呼び出し現場で起きる**実際のバグのパターン**を踏む seam のこと。利用できる seam が浅すぎる場合（複数呼び出し元が要るバグに単一呼び出し元のテスト、発火した連鎖を再現できない単体テスト）、そこでの回帰テストは偽の安心を生む。

**正しい seam が存在しないなら、それ自体が発見である。** 記録する。コードベースの構造がバグの固定を妨げている。次のフェーズに申し送る。

正しい seam がある場合：

1. 最小化した再現を、その seam での失敗するテストに変える
2. 失敗を見る。コードやフィクスチャの改変で赤を強制した場合は、改変が入ったことを pristine なコピーとの `diff` で証明してから信頼する
3. 修正を適用する
4. 通るのを見る
5. フェーズ1のフィードバックループを、元の（最小化していない）シナリオで再実行する

## フェーズ6：後片付け

完了を宣言する前に必須：

- [ ] 元の再現が再現しなくなった（フェーズ1のループを再実行）
- [ ] 回帰テストが通る（または seam の不在が記録されている）
- [ ] `[DEBUG-...]` の計装がすべて除去された（接頭辞で grep）
- [ ] 使い捨てプロトタイプが削除された（またはデバッグ用と明記した場所へ移動）
- [ ] 当たった仮説がコミット／PR のメッセージに書かれ、次のデバッグ担当が学べる
