# dotfiles-ai

Configuration repository for an AI development environment. It is the canonical source of the principles, rules, and skills shared by Cursor, Claude Code, and Muse Code, and each tool is deployed from here. The canonical sources live at the repository root (`rules.ja/` for rules, `skills.ja/` for skills). Rules are generated into the per-platform directories (`.cursor/`, `.claude/`); skills have no in-repository copy and are installed directly into the home-directory locations each tool reads.

This README is canonical in English; `README.ja.md` is kept in sync in the same commit (the same applies to `scripts/README.md` and `scripts/README.ja.md`).

## Roles

- **The human = the approver**: judges design, vulnerabilities, performance, and cost, and approves on evidence (test results, diffs, measurements)
- **Cursor = the approver's cockpit**: a window for reading diffs, following code, and approving. Its agent is used for git operations, where working in the IDE is easier to follow; its cloud features are not used
- **claude = the hands**: implements and tests
- **muse = the secretary**: does not implement. Decomposes tasks, dispatches them to claude, manages state, and reports. Its concrete duties are still to be decided

When the secretary's context grows long, it is written out to files, and sessions are disposable at any time. The source of truth for state is files, not conversation, and the only writer of state files is the secretary (muse).

## How principles are shared

- **Skills** use the Agent Skills standard (`SKILL.md`) and can be shared as-is across the three tools. Claude Code reads `~/.claude/skills/`; Cursor reads `~/.cursor/skills/` and also reads `~/.claude/skills/` as a compatibility path
- **Rules** differ in format per platform (Cursor uses `.mdc`, Claude Code uses `CLAUDE.md` and rules with `paths:`, muse uses plain Markdown). The canonical source is `rules.ja/`: each rule is split into `body.md` (the prose) and `meta.json` (the description, plus platform-specific fields separated into namespaces). `scripts/build-rules` generates each format from the canonical source, `scripts/install-rules` links those files into the home rule directories, and `scripts/install-skills` installs the skills. Rules and skills take effect from their home-directory installations (`~/.claude/rules/`, `~/.cursor/rules/`, `~/.claude/skills/`, `~/.cursor/skills/`); this repository holds the canonical sources and the scripts, and keeps no project-level rules or skills of its own. Edit the canonical sources, not the generated or installed files. The English editions for publication, `rules.en/` and `skills.en/`, are generated by `scripts/translate-rules` and `scripts/translate-skills`, and the canonical sources stay in Japanese

## Operating principles

1. **Keep the resident set lean**: instructions loaded at all times are only a map, verification commands, and scars from failures; details move to layers read when needed (skills, project specifications)
2. **Add only in response to observed failures**: when an agent makes a mistake, do not stop at fixing that instance. Promote it into one of these: a judgment miss becomes one line in a rule or skill, repeated work becomes a skill, and an exceptionless rule becomes a mechanism such as a hook
3. **Enforce exceptionless rules with mechanisms, not prompts**: when you want to write "always do X" in a rule, its place is a hook or a linter
4. **Create roles only where context isolation pays off**: build subagents only where parallelism, output isolation, or an unseen reviewer helps, and only from frequent work in your own workflow. Do not assemble a full set up front
5. **Control the flow**: do not generate more than the approver can review
