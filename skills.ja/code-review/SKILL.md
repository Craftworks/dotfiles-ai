ユーザーが与えた固定点と `HEAD` の間の diff を2軸でレビューする：

- **Standards**：コードがこのリポジトリの文書化された規約に従っているか
- **Spec**：コードが元の課題／仕様を忠実に実装しているか

両軸は**並行したサブエージェント**として実行し、互いのコンテキストを汚染しない。結果をこのスキルが集約する。各サブエージェントは新しいコンテキストウィンドウで始める。

仕様の出所（指示、仕様ファイル、タスクの記録）がこの会話で与えられていない場合は、ユーザーに確認する。

## 手順

### 1. 固定点を確定する

ユーザーが言ったものが固定点（コミット SHA、ブランチ名、タグ、`main`、`HEAD~5` 等）。指定が無ければ聞く。

diff コマンドを1回だけ確定する：`git diff <固定点>...HEAD`（3ドット。merge-base との比較になる）。コミット一覧も控える：`git log <固定点>..HEAD --oneline`。

先へ進む前に、固定点が解決できること（`git rev-parse <固定点>`）と diff が空でないことを確認する。悪い参照や空の diff は、2つのサブエージェントの中でなく、ここで失敗させる。

### 2. 仕様の出所を特定する

元の仕様をこの順で探す：

1. コミットメッセージ内の参照（`#123`、`Closes #45`、タスク ID 等）から辿れる仕様・タスク記録
2. ユーザーが引数で渡したパス
3. ブランチ名や機能名に一致する、`docs/`、`specs/`、`.scratch/` 配下の仕様ファイル
4. 何も見つからなければ、仕様がどこにあるかユーザーに聞く。無いと言われたら、**Spec** サブエージェントはスキップし、「仕様が利用できない」と報告する

### 3. 規約の出所を特定する

コードの書き方を文書化したファイルを、リポジトリ内からすべて探す。ルールファイル（`.cursor/rules/`、`rules.ja/` 等）、`CODING_STANDARDS.md`、`CONTRIBUTING.md` が存在すれば、必ず一覧に入れる。

リポジトリの文書に加えて、Standards 軸は常に下記の**スメルの基準線**を持つ：リポジトリが何も文書化していない場合にも適用される、Fowler のコードスメル（『Refactoring』第3章）の固定セットである。拘束する規則は2つ：

- **リポジトリが優先。** 文書化されたリポジトリの規約が常に勝つ。基準線が問題にしても、規約側がそれを是認している場合はスメルを抑止する
- **常に判断事項。** 各スメルはラベル付きのヒューリスティクス（「Feature Envy の可能性」）であり、硬い違反ではない。ここでの他の規約と同様、ツールが既に強制しているものは飛ばす

各スメルは「何であるか → 直し方」の形で書かれている。diff と照合すること：

- **Mysterious Name**（謎の名前）：何をするか／何を持つかが名前から分からない関数、変数、型。→ 改名する。正直な名前が思いつかなければ、設計が濁っている
- **Duplicated Code**（重複コード）：同じ形のロジックが変更内の複数の塊やファイルに現れる。→ 共通の形を抽出し、両方から呼ぶ
- **Feature Envy**（羨望）：自分のデータより他のオブジェクトのデータに手を伸ばすメソッド。→ そのメソッドを、羨望しているデータ側へ移す
- **Data Clumps**（データの塊）：同じ数個のフィールドや引数がいつも一緒に移動する（型になりたがっている）。→ 1つの型にまとめ、それを渡す
- **Primitive Obsession**（プリミティブへの執着）：独自の型を持つべきドメイン概念を、プリミティブや文字列で代用している。→ 概念に小さな独自の型を与える
- **Repeated Switches**（繰り返される分岐）：同じ型に対する同じ `switch`／`if` の連なりが変更内のあちこちに再現する。→ ポリモーフィズム、または両所で共有する1つのマップに置き換える
- **Shotgun Surgery**（散弾銃手術）：1つの論理的変更が、diff 内の多数のファイルへの散らかった編集を強いる。→ 一緒に変わるものを1つのモジュールに集める
- **Divergent Change**（変更の発散）：1つのファイルやモジュールが、無関係な複数の理由で編集される。→ 各モジュールが1つの理由で変わるよう分割する
- **Speculative Generality**（投機的な汎用性）：仕様に無い需要のために足された抽象、引数、フック。→ 削除する。本当の需要が来るまでインラインに戻す
- **Message Chains**（メッセージの連鎖）：呼び出し側が依存すべきでない長い `a.b().c().d()` のナビゲーション。→ 最初のオブジェクトの1メソッドの後ろに歩行を隠す
- **Middle Man**（仲介者）：ほとんど委譲するだけのクラスや関数。→ 取り除き、本当の対象を直接呼ぶ
- **Refused Bequest**（相続の拒否）：継承したものの大半を無視・上書きするサブクラスや実装者。→ 継承をやめ、合成を使う

### 4. 両サブエージェントを並行して起動する

両方のサブエージェント呼び出しを同時に出し、前景で実行して、返ってきた報告を集約する。

**Standards サブエージェントへの指示**に含めるもの：

- diff コマンド全文とコミット一覧
- 手順3で見つけた規約の出所ファイルの一覧に、**手順3のスメル基準線を全文貼ったもの**（サブエージェントは他にそれへアクセスする手段を持たない）
- 依頼文：「ファイル／塊ごとに報告する：(a) diff が文書化された規約に違反する箇所すべて（規約を引用する：ファイル＋規則）、(b) 見つけた基準線のスメル（名前を挙げ、塊を引用する）。硬い違反と判断事項を区別する：文書化された規約の違反は硬くなり得るが、基準線のスメルは常に判断事項であり、文書化されたリポジトリの規約は基準線に勝つ。ツールが強制済みのものは飛ばす。400語以内」

**Spec サブエージェントへの指示**に含めるもの：

- diff コマンドとコミット一覧
- 仕様のパス、または取得した内容
- 依頼文：「報告する：(a) 仕様が求めたのに欠けている・部分的な要件、(b) 求められていないのに diff にある振る舞い（スコープクリープ）、(c) 実装されているように見えるが実装が間違っていそうな要件。指摘ごとに仕様の行を引用する。400語以内」

仕様が無い場合は Spec サブエージェントを飛ばし、最終報告にその旨を書く。

### 5. 集約する

2つの報告を `## Standards` と `## Spec` の見出しの下に、そのまま、または軽く整えて提示する。所見を**混ぜたり、順位を付け直したりしない**。2軸を分けているのは意図的である（「なぜ2軸か」参照）。

最後に1行の要約を付ける：軸ごとの所見総数と、各軸内での最悪の指摘（あれば）。軸をまたいだ単一の勝者は選ばない：それは分離が防ごうとしている順位付けそのものである。

## なぜ2軸か

変更は一方の軸を通り、他方で落ちることがある：

- すべての規約に従うが、間違ったものを実装した → **Standards 合格、Spec 不合格**
- 課題が求めたとおりのことをするが、プロジェクトの慣習を壊した → **Spec 合格、Standards 不合格**

別々に報告することで、一方の軸が他方を覆い隠すのを防ぐ。
