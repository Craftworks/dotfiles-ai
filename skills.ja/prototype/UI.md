# UI Prototype

単一ルート上に**根本的に異なる UI バリエーションを複数**生成し、画面下部のフローティングバーで切り替える。ユーザーはブラウザでバリエーションを切り替えて眺め、1つを選ぶ（あるいは各バリエーションから部分を拾う）。残りは捨てる。

疑問が「どう見えるか」ではなくロジック／状態についてなら、この分岐は間違いである。[LOGIC.md](LOGIC.md) を使う。

## この形が合う場合

- 「このページはどう見えるべきか？」
- 「確定する前に、このダッシュボードの選択肢をいくつか見たい」
- 「設定画面の別レイアウトを試して」
- ユーザーが頭の中の曖昧なモックアップ3案の間で丸1日迷うような場面全般

## 2つの下位形状：下位形状 A を強く優先する

UI プロトタイプは、**アプリの残りの部分に接している**方がはるかに判断しやすい：本物のヘッダー、本物のサイドバー、本物のデータ、本物の密度。捨てルート単体は真空で、その中ではどのバリエーションも単体では問題なく見える。バリエーションを置ける既存ページが plausible に存在する限り、下位形状 A を既定にする。下位形状 B は、プロトタイプに本当に近くに置き場がない場合だけに使う。

### 下位形状 A：既存ページの調整（優先）

ルートはすでに存在する。バリエーションは**同じルート上**で、`?variant=` の URL 検索パラメータで出し分けて描画する。既存のデータ取得、パラメータ、認証はそのまま。差し替わるのは描画だけである。これが既定で、具体的な理由がない限りこちらを選ぶ。

プロトタイプ対象にまだページがなくても、**自然に既存ページの中に住むもの**（ダッシュボードの新しいセクション、設定画面の新しいカード、既存フローの新しいステップ）なら、やはり下位形状 A である。バリエーションをホストページの中にマウントする。

### 下位形状 B：新しいページ（最後の手段）

プロトタイプ対象に本当に住める既存ページがない場合（全く新しいトップレベルの画面、どこにも合理的に埋め込めないフロー等）にだけ使う。

プロジェクトがすでに使うルーティング規約に従って**捨てルート**を作る。新しいトップレベル構造を発明しない。プロトタイプだと分かる名前を付ける（パスやファイル名に `prototype` を含める等）。`?variant=` のパターンは同じ。

下位形状 B に決める前に健全性チェックをする：本当に埋め込める既存ページはないのか。空のルートは、データのあるルートなら露わになる設計上の問題を隠してしまう。

どちらの下位形状でも、画面下部のフローティングバーは同一である。

## 手順

### 1. 疑問と N を明記する

既定は**3バリエーション**。5を超えると根本的に異なる案ではなくノイズになり始めるので、そこを上限とする。

計画を1行で、プロトタイプの置き場かファイル先頭のコメントに書く：

> 「設定ページの3バリエーション。`?variant=` で切替、既存の `/settings` ルート上。」

これは、ユーザーがその場で反論できる場合でもできない場合でも機能する。

### 2. 根本的に異なるバリエーションを生成する

各バリエーションを起草する。各案に課す条件：

- ページの目的と、アクセスできるデータに沿うこと
- プロジェクトのコンポーネントライブラリ／スタイリングシステム（TailwindCSS、shadcn、MUI、プレーン CSS 等）を使うこと
- 明確な export 名のコンポーネントにすること（例：`VariantA`、`VariantB`、`VariantC`）

バリエーションは**構造的に**異なっていなければならない：異なるレイアウト、異なる情報階層、異なる主要アフォーダンス。色だけの違いではない。少しずつ変えたカードグリッド3案は UI プロトタイプではなく壁紙である。2案が似すぎたら、片方を「カードグリッドを使うな」と明示して作り直す。

### 3. 配線する

ルート上に単一のスイッチャーコンポーネントを作る：

```tsx
// 疑似コード。プロジェクトのフレームワークに合わせる
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

下位形状 A（既存ページ）：既存のデータ取得はすべてスイッチャーの上に残し、バリエーションごとに変わるのは描画されるサブツリーだけにする。

下位形状 B（新しいページ）：`/prototype/<name>` の捨てルートに同じスイッチャーをマウントする。

### 4. フローティングスイッチャーを作る

画面下部中央に固定配置する小さなバー。3つの要素を持つ：

- **左矢印**：前のバリエーションへ循環（末尾から先頭へ回る）
- **バリエーションラベル**：現在のバリエーションのキーと、そのバリエーションが名前を export していればその名前も表示する（例：`B (Sidebar layout)`）
- **右矢印**：次へ循環

振る舞い：

- 矢印のクリックで URL 検索パラメータを更新する（フレームワークのルーターを使う。Next なら `router.replace`、React Router なら `navigate` 等）。バリエーションが共有可能で、リロードしても安定するように
- キーボード：`←` と `→` の矢印キーでも循環する。`<input>`、`<textarea>`、`[contenteditable]` にフォーカスがあるときは矢印キーを横取りしない
- ページから視覚的に区別する（高コントラストのピル、控えめな影等）。評価対象のデザインの一部ではないことが明らかなように
- 本番ビルドでは隠す：`process.env.NODE_ENV !== 'production'` 等のチェックで出し分ける。迷子のプロトタイプがマージされてもバーがユーザーに出ないように

スイッチャーは単一の共有コンポーネントに置き、両下位形状で再利用できるようにする。置き場はプロジェクトで共有 UI が住む場所。

### 5. 渡す

URL（と `?variant=` のキー）を提示する。ユーザーは好きなときに切り替えて回る。面白いフィードバックは通常「B のヘッダーと C のサイドバーが欲しい」で、それこそが彼らの求める実際のデザインである。

### 6. 答えを保存し、片付ける

バリエーションが勝ったら、答え（どのバリエーションか、なぜか）を保存し、次に [SKILL](SKILL.md) の記述どおりにプロトタイプを保存する。勝者を本物のコードに取り込み、残りは main ではなく捨てブランチへ移す：

- **下位形状 A**：勝者を既存ページに取り込む。敗れたバリエーションとスイッチャーは main から落とす
- **下位形状 B**：勝ったバリエーションを本物のルートへ昇格させる。捨てルートとスイッチャーは main から落とす

バリエーション一式は一次資料なので、ゴミ箱ではなく捨てブランチに置く。バリエーションコンポーネントとスイッチャーを main ブランチに残すと、速く腐って次の読み手を混乱させるためである。

## 反パターン

- **色や文言だけが違うバリエーション。** それは微調整であってプロトタイプではない。本物のバリエーションは構造について意見が分かれる
- **バリエーション間でコードを共有しすぎる。** 共有の `<Header>` は構わないが、共有の `<Layout>` は趣旨を損なう。各バリエーションはレイアウトを捨てる自由を持つべきである
- **バリエーションを本物の変更操作に配線する。** 読み取り専用のプロトタイプで十分である。バリエーションが変更を必要とするならスタブに向ける：疑問は「どう見えるべきか」であって「バックエンドが動くか」ではない
- **プロトタイプをそのまま本番へ昇格させる。** バリエーションのコードはプロトタイプの制約（テストなし、最小限のエラー処理）で書かれている。取り込むときに正しく書き直す
