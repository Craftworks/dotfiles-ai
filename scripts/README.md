# scripts Directory Specification

This README is the specification of the scripts directory.

It holds the scripts that process the language editions of the rules and skills. The canonical sources are `rules.ja/` and `skills.ja/`; further editions (for example `rules.en/` and `skills.en/`) are generated from them by the translate scripts. `build-rules`, `install-rules`, `install-skills`, `translate-rules`, and `translate-skills` are implemented.

| Script | Job |
|---|---|
| `build-rules` | Deterministically generates the deliverables (Cursor and Claude formats) from the rule edition selected by `--lang` |
| `install-skills` | Installs the skills of the edition selected by `--lang` into the home skill directories as symbolic links |
| `install-rules` | Links the deliverables `build-rules` already wrote into the home rule directories |
| `translate-rules` | Translates the rule edition `rules.<from>/` into `rules.<to>/` (by default the canonical sources into English) |
| `translate-skills` | Translates the skill edition `skills.<from>/` into `skills.<to>/` (by default the canonical sources into English) |

## build-rules

Purpose: generate `.cursor/rules/<name>.mdc` and `.claude/rules/<name>.md` from `body.md` and `meta.json` in `rules.<lang>/<name>/`, where `<lang>` is the language selected by `--lang`.

Input/output contract:

- The input is the selected edition only. The output is a pure function of the input: the same input always produces the same bytes (idempotent)
- Generated files carry no marker header. Drift from the canonical sources is detected by `--check`, not by text inside the file
- `--check` writes nothing; it only verifies that the generated files match the selected edition, and exits with an error naming any file that has drifted
- `--lang <language>` selects the source edition `rules.<language>/`; the default is `en`. The language is not checked against a list: any language whose edition directory exists can be built. Given more than once, `--lang` exits with `lang: --lang was given more than once. pass it once`, before anything is read or written. The deliverables do not record which language they were built from, so building and installing are done back to back with the same language
- Reporting is part of the contract. A normal run prints what it did on stdout: a summary line (`wrote <count> files from rules.<lang> under <root>`) followed by the path of every file written. A successful `--check` prints `checked <count> files from rules.<lang> under <root>; all match; wrote nothing` followed by every path checked. Silent success is a defect: it is indistinguishable from nothing happening
- A failed `--check` prints a summary line, one line per problem, and the next action (`run without --check to write them.`) on stderr. A differing or missing file is named individually (`differs: <path>`, `missing: <path>`); when a whole output directory is missing or empty, the directory is named once (`missing: <dir>`, `empty: <dir>`) and the files under it are not listed. Empty means the directory has no entries. A directory that exists and contains anything, including an unrelated file, is not empty: each missing deliverable is named with `missing: <path>`. Problems are reported at the unit the operator acts on

Non-goals: translation, installation into the home directory, git operations, watch mode, incremental processing.

Conversion table (the canonical `meta.json` has a top-level `description` and a `cursor` namespace):

| meta.json | Cursor format (.mdc) | Claude format (.md) |
|---|---|---|
| `cursor.alwaysApply: true` | `alwaysApply: true` in frontmatter | No frontmatter |
| `cursor.globs` present | `globs` in frontmatter | Emitted as `paths` in frontmatter |
| Otherwise (description only) | Description only in frontmatter | No frontmatter |

Note: Claude Code's rule loading reads only `paths` in frontmatter; it does not read `alwaysApply`. Files placed in `~/.claude/rules/` are loaded resident. How auto rules (description only) are handled on the home side is an open question for the install design (pending verification by measurement).

Validation and errors:

- All rules are validated first. `meta.json` must be an object with a string `description` and an object `cursor`. Unknown keys are rejected at the top level and inside `cursor`. `cursor.globs`, when present, is a string or null; null means no globs. `cursor.alwaysApply`, when present, is a boolean. `body.md` must exist. Writing starts only after every rule passes. If any rule is invalid, the script exits with an error and no output files are written
- If `rules.<lang>` itself is missing, the script exits with an error and writes nothing
- Error messages take the form: rule name, cause, next action. A missing `rules.<lang>` is named `rules.<lang>` in that same form. The exit code reports success or failure

Implementation: Python 3, standard library only, a script file with no extension. The repository it works on is the one containing the script; there is no option to point it at another. Reading and validating a rule is in `scripts/rule_source.py`, shared with translate-rules so a rule is valid for both or for neither, with the same error lines; the script imports it from its own directory. JSON is read with the standard `json` module. Frontmatter values are emitted as unquoted plain scalars, with keys ordered description, globs, alwaysApply, matching the current .mdc files. It must run on both Mac and Windows.

Tests: built test-first. Golden-file comparison on three fixtures (alwaysApply / globs / description only); a regression run over a frozen snapshot of the real rules (inputs and expected outputs captured on 2026-11-21 under `scripts/tests/fixtures/real/` — the snapshot is the oracle, never the live outputs; the snapshot holds the Japanese sources, so this run passes `--lang ja`); assertions on the output reporting (the full summary line and every path a run says it wrote or checked); `--check` cases (clean, tampered, one missing file while a sibling remains, missing or empty output directories, and a directory that contains only unrelated files); and error cases (missing file, invalid JSON, unknown key, `meta.json` that is not an object, `description` missing or not a string, `cursor` missing or not an object, an unknown key under `cursor`, `globs` that is not a string, `alwaysApply` that is not a boolean, a missing edition directory, and a mix of valid and invalid rules — verifying that nothing is written); and `--lang` cases (the default builds the English edition, an explicit `--lang ja` builds the Japanese edition, and a repeated `--lang` exits with the sentence above and writes nothing). The script under test is copied into each fixture repository's `scripts/` directory and invoked from there.

Done conditions:

1. Against the frozen snapshot of the real rules, the generated files match the expected outputs byte for byte
2. Running it twice in a row produces zero diff on the second run
3. `--check` exits successfully when the outputs match the selected edition, and exits with an error when a generated file has been edited by hand, a file is missing, or an output directory is missing or empty — naming the drifted file, or the directory alone when the directory itself is missing or has no entries. A directory that still contains an unrelated file is not that case: each missing deliverable is named
4. On invalid input it exits with an error and writes no output files at all
5. On a fixture with globs, the Claude format carries a correct `paths` frontmatter

## install-skills

Purpose: install the skills in `skills.<lang>/<name>/` into the home skill directories (`~/.claude/skills/` and `~/.cursor/skills/`) as one symbolic link per skill, pointing at the skill directory in this repository. Skills need no format conversion, so installation creates links, never copies: the edition in the repository stays the only real files, and editing a skill takes effect without reinstalling.

Input/output contract:

- The unit of installation is the skill directory. A link covers everything in it (SKILL.md and any auxiliary files); files added inside a skill need no reinstall. Only adding or removing a whole skill does
- Link targets are absolute paths under the repository containing the script. If the repository moves, the links break; `--check` reports them and a normal run repairs them
- The script manages only symbolic links that point into one of this repository's skill editions (a `skills.<lang>/` directory, for any language). It never creates, overwrites, or deletes a real file or directory, and never touches a link that points elsewhere. Entries owned by others (for example `~/.claude/skills/synced/`, where Claude Code keeps the skills it downloads from the user's claude.ai account) are outside its management
- A link that points into a different edition of this repository than the selected one is a wrong target: a normal run repairs it to the selected edition, and `--check` reports it as `differs`
- A destination entry that blocks a skill — a real file or directory, or a link pointing outside this repository — is a conflict. Conflicts are detected before anything is changed: if any skill is invalid or any conflict exists on a selected destination, the run exits with an error and no link is created, repaired, or removed
- A link at a selected destination that points into one of this repository's skill editions, for a skill that does not exist in the selected edition, is stale. A normal run removes it; `--check` reports it. Only links into this repository are ever removed
- Reporting is part of the contract. A normal run prints a summary line (`installed <count> skills from skills.<lang> under <home>`) followed by the path of every link in place, and one `removed: <path>` line for each stale link it removed. A successful `--check` prints `checked <count> links from skills.<lang> under <home>; all match; wrote nothing` followed by every path checked. Silent success is a defect: it is indistinguishable from nothing happening
- A failed `--check` prints a summary line, one line per problem, and the next action (`run without --check to install the links; conflicting entries must be removed by hand.`) on stderr. Problems are named at the unit the operator acts on: `missing: <path>` when no entry exists, `differs: <path>` when a link points at the wrong target or is broken, `stale: <path>` for a link whose skill is gone, `conflict: <path>` for a blocking entry the script must not touch. When a destination directory itself is missing, the directory is named once (`missing: <dir>`) and the links under it are not listed
- Running it twice in a row changes nothing on the second run (idempotent)
- `--tool <cursor|claude>` narrows the run to one destination. `cursor` is `<home>/.cursor/skills`; `claude` is `<home>/.claude/skills`. Omit `--tool` and both destinations are selected, which is every case above. The unselected destination is not part of the run: the script does not create it, does not look inside it, and does not report it. A conflict or a stale link there does not affect the run, and the entries there are identical before and after, including when the run fails. `--tool` with a value other than `cursor` or `claude` exits with `tool: unknown tool "<value>". pass --tool cursor or --tool claude`. `--tool` given more than once exits with `tool: --tool was given more than once. pass it once`. Either error is printed before any destination is read or written, and nothing is changed. The summary still counts skills on a normal run and links on `--check`; with one destination those two numbers are equal, and every path printed is under the selected destination
- `--lang <language>` selects the edition `skills.<language>/` to install; the default is `en`. The language is not checked against a list: any language whose edition directory exists can be installed. `--lang` given more than once exits with `lang: --lang was given more than once. pass it once`, before any destination is read or written, and nothing is changed

Non-goals: copying skill files, installing rules (`install-rules` links them), deleting real files or directories, managing plugin skills or claude.ai-synced skills, watch mode, Windows support (symbolic links there need privileges this setup does not assume).

Validation and errors:

- All skills are validated first. `skills.<lang>` must exist. Every subdirectory of `skills.<lang>/` is a skill: it must contain a `SKILL.md` whose frontmatter, read as simple `key: value` lines, has a `name` and a `description`, both non-empty strings, and the `name` must equal the directory name. A non-blank frontmatter line without a colon, a frontmatter with no closing `---`, and a key given twice are errors, not lines to skip or overwrite. Other frontmatter keys are allowed (the skill format is an open standard with optional keys such as `disable-model-invocation`). A skill named `synced` (in any capitalisation) is rejected when `claude` is a selected destination: Claude Code reserves that name under `~/.claude/skills/` for synced skills. When the run is `--tool cursor` only, that name is an ordinary skill. Linking starts only after every skill passes and no conflict exists on a selected destination
- Error messages take the form: skill name, cause, next action. A missing `skills.<lang>` is named `skills.<lang>` in that same form. The exit code reports success or failure

Implementation: Python 3, standard library only, a single file (no extension), the same conventions as build-rules. The command line is `install-skills [--home <home directory>] [--tool <cursor|claude>] [--lang <language>] [--check]`; the repository it works on is the one containing the script, and `--home` defaults to the user's home directory and exists so tests can install into a temporary home. Frontmatter is read as simple `key: value` lines; no YAML library is used. macOS is the target platform.

Tests: built test-first, in the style of the build-rules tests (the script is copied into a temporary repository's `scripts/` directory and invoked as a subprocess from there, against a temporary `--home` directory). Cases: a fresh install links every skill at both destinations with the correct targets; a second run changes nothing; `--check` passes on the installed state and fails, naming the path, for a missing link, a wrong-target link, a stale link, and a conflict, and names the directory alone when a destination directory is missing; a normal run removes a stale link and repairs a link broken by moving the repository; a conflict (a real directory at a destination) blocks the whole run and nothing is linked; invalid inputs (missing SKILL.md, missing or empty description, a name that differs from the directory name, a frontmatter line without a colon, a frontmatter with no closing `---`, a duplicate key, a skill named `synced`, a missing `skills.<lang>`, and a mix of valid and invalid skills) exit with an error and change nothing; entries the script does not own (a real `synced/` directory, a foreign link, a real file) are unchanged by every run, including failed ones; assertions on the output reporting (the full summary line and every path a run says it installed or checked); a run over the real `skills.<lang>` into a temporary home, where every skill in that edition ends up linked and every link resolves to a directory containing a SKILL.md (the oracle is the edition itself: the output is links, not bytes, so there is no golden snapshot); and `--tool` cases (cursor only and claude only each link just that destination and leave the other untouched, a conflict or stale link on the unselected side does not block and stays, repair and stale removal apply only to the selected side, `--check` names only the selected destination, a skill named `synced` is rejected for claude and accepted for cursor only, and an unknown or repeated `--tool` exits with the sentence above and changes nothing); and `--lang` cases (the default installs from `skills.en`, `--lang ja` installs from `skills.ja`, a link pointing into the other edition is repaired to the selected edition, a link whose skill is absent from the selected edition is removed as stale, and a repeated `--lang` exits with the sentence above and changes nothing).

Done conditions:

1. Into an empty home, with `--tool` omitted, every skill in the selected edition (`skills.en` by default) is linked at both destinations, and every link resolves to that skill's directory in the repository
2. Running it twice in a row creates, repairs, and removes nothing on the second run
3. `--check` exits successfully on the installed state, and exits with an error naming the path when a link is missing, points at the wrong target, or is stale, when a blocking entry conflicts, and naming the directory alone when a destination directory itself is missing
4. On invalid input or any conflict, it exits with an error and changes nothing: no link is created, repaired, or removed
5. Entries the script does not own — real files and directories, links pointing outside this repository, and `synced/` — are identical before and after every run, including failed runs
6. With `--tool cursor` or `--tool claude`, only that destination is linked, checked, repaired, or cleaned. The other destination is identical before and after, including when the run fails. An unknown or repeated `--tool` changes nothing

## install-rules

Purpose: link the deliverables `build-rules` already wrote (`.cursor/rules/<name>.mdc` and `.claude/rules/<name>.md`) into the home rule directories (`~/.cursor/rules/` and `~/.claude/rules/`), one symbolic link per file. Installation does not generate those files and does not copy them. They stay under `.cursor/` and `.claude/` in the repository, which is where `build-rules` writes them.

Input/output contract:

- The set of rules is the subdirectories of `rules.<lang>/`, where `<lang>` is the language selected by `--lang`. The deliverables a run links are the ones `build-rules` wrote; the deliverables do not record which language they were built from, so building and installing are done back to back with the same language. For each selected destination that rule's deliverable must already exist. A missing deliverable is `<name>: missing <path>. run build-rules`. The run then changes nothing, including when another rule's deliverable is already present. The deliverable files themselves are never modified
- Link targets are absolute paths under the repository containing the script. If the repository moves, the links break; `--check` reports them and a normal run repairs them
- The script manages only symbolic links that point at a deliverable under `.cursor/rules/` or `.claude/rules/`. It never creates, overwrites, or deletes a real file or directory, and never touches a link that points elsewhere
- A destination entry that blocks a rule file — a real file or directory, or a link that does not point at a deliverable — is a conflict. Conflicts are detected before anything is changed: if any selected deliverable is missing or any conflict exists on a selected destination, the run exits with an error and no link is created, repaired, or removed
- A link at a selected destination that points at a deliverable for a rule no longer in `rules.<lang>/` is stale. A normal run removes the link; `--check` reports it. Only such links are removed. The deliverable file in the repository is left in place
- Reporting is part of the contract. A normal run prints `installed <count> files from rules.<lang> under <home>` followed by the path of every link in place, and one `removed: <path>` line for each stale link it removed. A successful `--check` prints `checked <count> links from rules.<lang> under <home>; all match; wrote nothing` followed by every path checked. Silent success is a defect: it is indistinguishable from nothing happening
- A failed `--check` prints `links do not match rules.<lang>. --check changes nothing.`, one line per problem, and the next action (`run without --check to install the links; conflicting entries must be removed by hand.`) on stderr. Problems are named at the unit the operator acts on: `missing: <path>` when no entry exists, `differs: <path>` when a link points at the wrong deliverable, `stale: <path>` for a link whose rule is gone, `conflict: <path>` for a blocking entry the script must not touch. When a destination directory itself is missing, the directory is named once (`missing: <dir>`) and the links under it are not listed
- Running it twice in a row changes nothing on the second run (idempotent)
- `--tool <cursor|claude>` narrows the run to one destination. `cursor` is `<home>/.cursor/rules`; `claude` is `<home>/.claude/rules`. Omit `--tool` and both destinations are selected. The unselected destination is not part of the run: the script does not create it, does not look inside it, and does not report it. A conflict or a stale link there does not affect the run, and a deliverable is required only for a selected destination. `--tool` with a value other than `cursor` or `claude` exits with `tool: unknown tool "<value>". pass --tool cursor or --tool claude`. `--tool` given more than once exits with `tool: --tool was given more than once. pass it once`. Either error is printed before anything is read or written, and nothing is changed. A normal run counts files and `--check` counts links; with one destination those two numbers are equal, and every path printed is under the selected destination
- `--lang <language>` selects the edition `rules.<language>/` whose rule set the run uses; the default is `en`. The language is not checked against a list: any language whose edition directory exists can be selected. `--lang` given more than once exits with `lang: --lang was given more than once. pass it once`, before anything is read or written, and nothing is changed

Non-goals: generating the deliverables (`build-rules` does that), copying bytes into the home directory, deleting real files or directories, deleting deliverables from the repository, translation, watch mode, Windows support (symbolic links there need privileges this setup does not assume).

Implementation: Python 3, standard library only, a single file (no extension). The command line is `install-rules [--home <home directory>] [--tool <cursor|claude>] [--lang <language>] [--check]`; the repository it works on is the one containing the script, and `--home` defaults to the user's home directory and exists so tests can install into a temporary home. macOS is the target platform.

Tests: built test-first, in the style of the install-skills tests (the script is copied into a temporary repository's `scripts/` directory and invoked as a subprocess from there, against a temporary `--home` directory). Cases: a fresh install links every deliverable at both destinations with an absolute target, and reading the link returns the deliverable's bytes; a second run changes nothing; `--check` passes on the installed state and fails, naming the path, for a missing link, a wrong-target link, a stale link, and a conflict, and names the directory alone when a destination directory is missing; a normal run removes a stale link and leaves the repository deliverable in place, and repairs a link broken by moving the repository; a conflict blocks the whole run and nothing is linked, repaired, or removed; a missing `rules.<lang>` and a missing deliverable (including one rule missing its file while a sibling is complete) exit with an error and change nothing; a real file whose name is not a rule is unchanged; and `--tool` cases (cursor only and claude only each link just that destination, cursor does not require the Claude deliverable, a conflict or stale link on the unselected side does not block and stays, repair and stale removal apply only to the selected side, `--check` names only the selected destination, and an unknown or repeated `--tool` exits with the sentence above and changes nothing); and `--lang` cases (the default uses the English edition's rule set, an explicit language uses that edition's, and a repeated `--lang` exits with the sentence above and changes nothing).

Done conditions:

1. Into an empty home, with `--tool` omitted, every rule in the selected edition (`rules.en` by default) is linked at both destinations, and every link resolves to that rule's deliverable in the repository
2. Running it twice in a row creates, repairs, and removes nothing on the second run
3. `--check` exits successfully on the installed state, and exits with an error naming the path when a link is missing, points at the wrong deliverable, or is stale, when a blocking entry conflicts, and naming the directory alone when a destination directory itself is missing
4. On a missing `rules.<lang>`, a missing deliverable, or any conflict, it exits with an error and changes nothing: no link is created, repaired, or removed, and no deliverable is modified
5. Entries the script does not own — real files and directories, and links that do not point at a deliverable — are identical before and after every run, including failed runs
6. With `--tool cursor` or `--tool claude`, only that destination is linked, checked, repaired, or cleaned, and only that destination's deliverable is required. The other destination is identical before and after, including when the run fails. An unknown or repeated `--tool` changes nothing

## translate-rules

Purpose: translate the rule edition `rules.<from>/` into `rules.<to>/`. The defaults are `--from ja` and `--to en`: the Japanese canonical sources into the English edition. Which editions exist and which one the agents follow are separate choices (the translate scripts generate editions; `build-rules` and the install scripts select one with `--lang`); this script only translates, from the language given to the language given.

Input/output contract:

- The scope is `body.md` and the `description` in `meta.json`. `basis.md` (the rationale) is a document for the approver and is out of scope
- The output is `rules.<to>/<name>/body.md` and `rules.<to>/<name>/meta.json` only. Nothing else is stored under `rules.<to>/`
- `description` is translated. The `cursor` namespace is copied as the same JSON, never translated: when only `cursor` changed, `rules.<to>/<name>/meta.json` is rewritten with the new `cursor` and the previous target description, without a translator call. Headings and identifiers that are already in the target language stay as written
- Line contract: the target text has exactly one line for each source line, in the same order. A blank line stays blank, and each line keeps its Markdown marker (heading level, list marker, table row, code fence). Punctuation follows the source: no trailing period is added where the source has none. Source-language text inside a code fence, including a comment, is translated. Code tokens and string literals stay. This contract is what makes keeping the previous target text mechanical
- The baseline is taken from git, not from a stored copy. For each rule, the base commit is the last commit that changed `rules.<to>/<name>/body.md`. The previous source is `rules.<from>/<name>/` at that commit, and the previous target is `rules.<to>/<name>/` at that same commit, not the working tree, so the pair always matches line for line. The prerequisite is that the target edition is committed after it is translated, which is also when it is reviewed
- A rule is a target when its current source (`body.md` or `description`) differs from the previous source, or when `rules.<to>/<name>/` does not exist in the working tree (it is then translated in full). Rule names given on the command line narrow the run to those rules; an unknown name is an error
- Where the source is unchanged, the previous target is kept byte for byte. The previous and current source are compared line by line; each unchanged line takes the previous target line at the same position, and only changed or added lines take the new translation. The translator receives the whole current source, and, for consistent terms, the previous target of the unchanged lines only, as [source, target] pairs. The old target of a changed line is never shown: measured on 2026-11-23 with the default pair (Japanese into English), Haiku shown it copied the old line instead of translating the new source (2 of 2 runs). Review is the diff of the targeted files under `rules.<to>/`
- A rule whose `rules.<to>/<name>/` has uncommitted changes is an error (`commit or discard rules.<to>/<name>, then rerun`): keeping lines from a target text that does not match the base pair would misplace them. A base pair whose line counts differ is also an error; deleting `rules.<to>/<name>/` makes the rule a full translation. Nothing is retranslated in full silently
- The translator is the Claude Code command `claude -p`, using the Sonnet model. Measured on 2026-11-23 with the JSON shape below, Haiku and Sonnet both kept the line contract in 18 of 18 runs; Sonnet kept the source's emphasis and added no trailing period where Haiku added 2, at about 1.7 yen per rule against 0.13 (at 159 yen per dollar; with the Claude Code login this is drawn from the plan's usage, and the yen are the API equivalent). The model and the prompt are constants in `scripts/translator.py`, shared with translate-skills, and that module is their only definition. Authentication is the Claude Code login already on the machine. `--bare` is not used: it reads only `ANTHROPIC_API_KEY`, never the login
- The translator runs isolated: its working directory is an empty temporary directory, and it is started with `--tools "" --strict-mcp-config --setting-sources "" --disable-slash-commands --no-session-persistence --system-prompt <prompt>`. CLAUDE.md, rules, hooks, MCP servers, and skills are not loaded, and the translator has no tool with which to touch files. Measured on 2026-11-23: the default start sends about 32K tokens of context even for a one-word reply; isolated, about 3K
- One rule is one translator call. The request on standard input and the answer on standard output are a JSON object with a `description` string and a `body` array holding one string per line. Measured on 2026-11-23 with Haiku: plain lines (description on line 1) kept the line contract in 13 of 18 runs, because the description was merged into or swapped with the `# Title` heading; this JSON shape kept it in 18 of 18. Calls run one at a time, and a rule that is not a target makes no call at all. Measured on 2026-11-23 with Sonnet: 5.8 seconds per rule on average (7.3 at most), about 3 seconds of which is process start; a run with nothing changed takes under 1 second
- A call fails when the command is missing, exits non-zero, exceeds the timeout (120 seconds by default, `--timeout <seconds>`), or prints output that breaks the contract: empty output, output that is not a JSON object of that shape, a different line count or Markdown marker, source-language characters left in the text (Japanese characters for the default pair), or an empty description. A failed call is not retried; the run is all or nothing, so rerunning is safe
- All targets are translated and validated before anything is written. If any rule fails, the run writes nothing and leaves `rules.<to>/` as it was. Files are written through a temporary file and replaced, so an interrupted run leaves no half-written file. Errors name the rule, the cause, and the next action (for a failed call: make `claude -p` succeed, then rerun). The source edition is validated by the shared `rule_source.py`, as in build-rules, before any call
- Reporting is part of the contract. While running, it prints one line per rule as it goes (`translating <name>`, `copying cursor of <name>`, or `unchanged <name>`), because a run of several rules takes a minute or more. It then prints a summary line in the form build-rules uses (`wrote <count> files from rules.<from> under <root>`) followed by the path of every file written. A run with no targets says so and writes nothing

Non-goals: Google Translate, DeepL, and any translator that requires an API key; removing `rules.<to>/<name>/` when a rule is removed from `rules.<from>/` (that is done by hand); git operations that change the repository (the script only reads history; committing is the user's); parallel calls; watch mode.

Implementation: Python 3, standard library only, a script file with no extension, the same conventions as build-rules, including the shared `scripts/rule_source.py` for reading and validating the source edition. The command line is `translate-rules [--from <language>] [--to <language>] [--translator <command>] [--timeout <seconds>] [<name>...]`; the repository it works on is the one containing the script. `--from` defaults to `ja` and `--to` to `en`, and either one given more than once exits with `from: --from was given more than once. pass it once` or `to: --to was given more than once. pass it once`, before anything is read or written; `--translator` replaces the `claude` command and exists so tests can run a fake translator, which is called with the same arguments and standard input. It must run on both Mac and Windows: the command is resolved with `shutil.which` (`claude.exe` or `claude.cmd`), standard input and output are UTF-8 explicitly, line endings are normalised to LF on reading and written as LF, and a timed-out translator is killed together with its children. If `taskkill` fails, or the process is still running 10 seconds after the kill, the error names that process instead of waiting forever (`scripts/tests/test_translator.py`).

Tests: built test-first. The script is copied, with the shared modules, into a temporary git repository's `scripts/` directory and invoked as a subprocess from there, with `--translator` pointing at a fake translator; the real `claude` is not called by the automated tests. Cases: a new rule is translated in full; a changed line is replaced while every unchanged line keeps the previous English byte for byte; a changed description alone; a changed `cursor` alone is copied with no translator call; an unchanged rule makes no translator call; rule names narrow the run and an unknown name is an error; uncommitted changes in `rules.<to>/<name>` and a base pair with differing line counts are errors; a root that is not a git repository and a base commit without `rules.<from>/<name>` are errors; the old English of a changed line is never shown to the translator; the translator failing, exiting non-zero, printing empty output or output that is not JSON, a wrong line count, a changed marker, leftover source-language text, or exceeding the timeout each write nothing; a mix of rules where one fails writes nothing for any of them; assertions on the output reporting (the progress lines, the full summary line, and every path written); and a run with an explicit pair (`--from en --to fr` in the temporary repository) translating that pair into `rules.fr/`. A manual smoke run with the real `claude -p` on one rule checks the flags and the login.

Done conditions:

1. A changed rule produces a target text in which every unchanged source line keeps its previous target byte for byte
2. With no change under `rules.<from>/`, a run makes no translator call and writes nothing
3. On any failed call or invalid input, it exits with an error naming the rule, the cause, and the next action, and `rules.<to>/` is identical before and after
4. The translator starts without CLAUDE.md, rules, hooks, MCP servers, skills, or tools
5. It runs on both Mac and Windows

## translate-skills

Purpose: translate the skill edition `skills.<from>/` into `skills.<to>/`. The defaults are `--from ja` and `--to en`: the Japanese canonical sources into the English edition. Which edition `install-skills` links is that script's own `--lang` choice; this script only translates.

Input/output contract:

- One translator call is one Markdown file, using the same JSON shape, model, prompt, and isolation flags as translate-rules (`scripts/translator.py`). A skill is not one call: a long combined request is outside the measured line contract
- `SKILL.md` translates `description` and the body. `name` stays the directory name and is not sent. Other frontmatter keys are copied. `basis.md` is not part of the edition. A file that is not Markdown is copied byte for byte and makes no call
- Every line of a Markdown file is sent, including a line inside a code fence. Source-language text there is translated, including a comment. Code tokens and string literals stay. A fence marker stays a fence marker, and text that is already English stays, because that is the line contract in `scripts/translator.py`
- The line contract, the git baseline, and the splice are per file. The baseline is the last commit that changed `skills.<to>/<skill>/<path>`. Unchanged lines keep the previous target byte for byte. The old target of a changed line is not sent. Uncommitted changes under `skills.<to>/<skill>/` are an error and the run writes nothing
- Calls run `--jobs` at a time (default 4). The first line is `translating <count> file, <jobs> at a time` for one file and `translating <count> files, <jobs> at a time` for more, then `translating <skill>/<path>` as each call starts, `copying <skill>/<path>` for a copied file, and `unchanged <skill>/<path>` for a file that needs nothing. A failed call stops the calls still running, starts no new call, and leaves `skills.<to>/` unchanged. The error names the file, the cause, and the next action (`make claude -p succeed, then rerun`). A process that could not be stopped follows on its own line, ending in `stop process <pid> by hand`
- After every call has succeeded, the run prints `wrote <count> files from skills.<from> under <root>` and every path written. A run with nothing to do says so and writes nothing
- `SKILL.md` is validated with `scripts/skill_source.py`, the same lines install-skills uses, before any call

Non-goals: installing an edition (`install-skills` does that), translating `basis.md`, one request that holds every file, removing `skills.<to>/<skill>/` when a skill is removed from `skills.<from>/` (that is done by hand), parallel calls inside translate-rules (that command stays one call at a time).

Implementation: Python 3, standard library only. The command line is `translate-skills [--from <language>] [--to <language>] [--translator <command>] [--timeout <seconds>] [--jobs <n>] [<name>...]`; the repository it works on is the one containing the script. `--from` defaults to `ja` and `--to` to `en`, and either one given more than once exits with `from: --from was given more than once. pass it once` or `to: --to was given more than once. pass it once`, before anything is read or written. `--jobs` below 1 exits with `jobs: --jobs must be at least 1. pass --jobs 4` and changes nothing.

Tests: the script is copied, with the shared modules, into a temporary git repository's `scripts/` directory and run as a subprocess from there, with a fake `--translator`. The real `claude` is not called. Cases: a new `SKILL.md` keeps `name` and translates `description` and the body; a fence interior is in the request and translated in the output, `basis.md` is omitted, and a shell script is copied; an unchanged skill makes no call; when a file is translated, the count line comes before the `unchanged` and `copying` lines; a changed line is new and the old English of that line is not in the prompt; two calls overlap under `--jobs 2`, and a failing call writes nothing; `--jobs 0` and a missing `SKILL.md` make no call; an explicit `--from en --to fr` run creates `skills.fr/` from `skills.en/`.

## How this specification is kept

It records the "why" and the contracts. The details of behavior have their canonical source in the tests, and the method of implementation in the code.
