# Change Discipline

## Before coding

- ゴールを一文で言う。完了条件（何がどうなれば終わりか）を決める
- 既存の同種実装を先に読む。流儀が分かれたら多数派/最近の正しい方に寄せる
- 不明点は推測で埋めず、コード・ドキュメント・実行結果で確認する

## While coding

- 1変更 = 1意図。無関係なリフォーマットやリネームを混ぜない
- 最小差分でゴールに達する。ついで修正は別変更にする
- 公開契約（API・型・CLI・ファイル形式）を壊すなら明示し、移行を用意する
- 承認者がレビューできる量を超えて生成しない
- README は入口だけを持つ（目的、使い方、他文書へのポインタ）。規範は置かない
- なぜ・契約・非目標・完了条件は SPEC に置く
- 作業物に恒久のファイル名を与えない

## Robustness gate

- サイレントに失敗しない（握りつぶし・空 catch・常時成功フォールバック禁止）
- 信頼境界（入力・ネットワーク・ファイル・他プロセス・環境変数）で検証する
- 不確かなら推測で進めない（確認してから書く）

## Security gate

- 秘密情報（APIキー、トークン、パスワード、秘密鍵）をソース・コミット・ログ・エラーメッセージ・スクショに出さない
- 権限は最小にする。広い権限・世界公開・デバッグ用バックドアを既定にしない
- 依存（パッケージ・バイナリ・スクリプト）を増やすときは必要理由を言い、メンテ状況と権限（何にアクセスするか）を確認する
- 信頼できない入力はコマンド・パス・クエリ・HTMLにそのまま渡さない

## Done means

- 動作確認の手段がある（コマンド、テスト、手動手順のいずれか）
- 失敗時に次の人が追える（エラー、ログ、または説明）
- 一時的な探索コードやデバッグ残骸を残していない
- 差分に秘密情報や不用意な広権限が混ざっていない
- 仕様は契約の水準まで圧縮してある。テストが固定済みの細部（エラー文面、報告形式、ケースの列挙）は残さない
- 文を残すか削るかの判定：その文に違反するのに全テストを通る実装を想像できるなら、文は契約として残すか、先にテストを強くする

## Maintaining rules and skills

- ルールやスキルに行を足すのは、観測した失敗への対応のときだけ。判断のミスはルールかスキルの1行に、繰り返す作業はスキルに、例外のないルールはフック・リンタ・型で担保する
